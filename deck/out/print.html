Why it matters at all
  • Programs need memory to hold their data and their objects.
  • Every new allocates memory that must eventually be released.
  • In C / C++ you call free() yourself — forget it and you leak or crash.
  • Java does it for you: the Garbage Collector reclaims memory automatically.
You never call free() in Java — but memory is still finite, so something has to clean up.

Where does Java keep everything?

Two areas — the Stack for execution, the Heap for objects. Only the Heap is garbage-collected.

The 30-second model
  • STACK — one per thread, per method call.
  • Holds locals, parameters and references to objects.
  • HEAP — shared memory for objects and arrays.
  • Only the Heap is managed by the Garbage Collector.
Mental model: Stack = what you are doing now  ·  Heap = what you created.

Garbage = unreachable.

Nobody can reach the object any more — so it becomes eligible for collection.

An unreachable object becomes eligible for GC.
Drop the last reference → the object floats away
BEFORE · reachable
user User object
✓ GC keeps it — someone can reach it

Eligible ≠ deleted — the GC still has to run.
Setting user = null does NOT delete the object — it only cuts the last rope. The collector frees it later.
06 — Reachability & GC Roots
JJava Memory Management · Garbage Collector
Java Memory Management — Garbage Collector YouCode · Java Track 06 / 15
Can the GC reach it?

Every collection starts from GC Roots and follows references. No path = garbage.

Reachability graph — the only question the GC asks
GC ROOT Object A Object B
✓ path from a root → reachable → GC keeps both
Object C no path from any root → UNREACHABLE
The GC traces the graph — it never asks “will you use this again?”, only “can I reach it?”
Common GC roots (you don't memorise internals)
  • Locals in active stack frames
  • Static fields of loaded classes
  • Active threads themselves
  • JVM-internal roots (JNI, …)
Still referenced, even once, means it stays — usefulness is irrelevant.
“Still referenced? Sorry, you're staying.”

The classic 3-step model behind (almost) every collector — find the living, free the dead, tidy up.

08 — Generational GC
JJava Memory Management · Garbage Collector
Java Memory Management — Garbage Collector YouCode · Java Track 08 / 15
Most objects die young.

So the Heap is split by age — clean the nursery often, disturb the elders rarely.

Why generations exist
  • New objects start in Eden (young generation).
  • A minor GC clears the young gen fast — most objects are already dead.
  • Survivors age in S0 / S1, then get promoted to Old.
  • The Old generation holds long-lived data, collected rarely.
Collecting 500 MB of young garbage beats scanning a 10 GB heap every time.
Young (Eden + S0/S1) → promotion → Old
“Most Java objects have a very short career.”
09 — Collector zoo
JJava Memory Management · Garbage Collector
Java Memory Management — Garbage Collector YouCode · Java Track 09 / 15
Pick your collector.

Same job — find garbage. Different trade-offs between throughput and pause time.

Serial GC
  • Simple · single-threaded
  • Small apps · tiny heaps
Parallel GC
  • Multi-threaded stop-the-world
  • Max throughput batch jobs
G1 GC ★
  • Region-based, default JDK 9+
  • Balances latency + throughput
ZGC
  • Sub-millisecond pauses
  • Huge heaps · concurrent
Shenandoah
  • Low-pause, concurrent
  • Responsive services
Rule of thumb: default to G1 — reach for ZGC / Shenandoah only when pauses hurt. ★ = the one we zoom into next.

G1 cleans the dirtiest first.

Garbage-First GC — the default since JDK 9. Regions, not generations-in-concrete.

G1 in 20 seconds
  • G1 = Garbage-First. Heap split into equal regions.
  • A region can be Eden, Survivor, Old or Humongous.
  • G1 collects the regions with the most garbage first.
  • Goal: big reclamation within a pause-time target.
